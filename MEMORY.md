# 42-Studenti — Memory

_Last updated: 2026-11-24_

## Overview & Tech Stack
- Type: Web App (student community portal for 42 Roma). UI 100% Italian + Roman slang (romanesco). Two switchable 90s themes (Classico Romano / SPQR Hacker).
- Monorepo:
  - `api/` (port 9000): Python 3.11+ (runs on 3.14), FastAPI, SQLAlchemy 2.0 async + asyncpg, Alembic, Pydantic v2, JWT in httpOnly cookie. Vendored local 42 client at `api/vendor/42api` (the `intra42` pkg from Shadowaker/42api, **v0.1.5 + the `events_users`/`from_access_token` PR work + our `events.for_campus`** extension), installed editable. `app/intra_user.py` uses `AsyncClient.from_access_token` for user-scoped event sign-up.
  - `web/` (port 3000): Next.js 15 (App Router, TS strict), Tailwind CSS v4, shadcn-style hand-built UI (Radix Dialog, CVA), dual theme via `[data-theme]`.
- Database: PostgreSQL (Supabase, Postgres only — no Supabase Auth/RLS). `DATABASE_URL` (asyncpg, runtime) + `DIRECT_URL` (Alembic). Tests use in-memory SQLite (aiosqlite).
- Tooling: `pip`/venv + `requirements.txt`(+`.lock`); pnpm. Tests: pytest (api), `tsc`/eslint/`next build` (web).
- Design source of truth: `assets/classic.html`, `assets/hacker.html`, `assets/rome-pixel.png`.

## Architecture Decisions & Technical Notes
- No roles: flat `User`; authorization is ownership-only, enforced server-side (IDOR-safe). Client gating (`GET /me`) is UX only.
- The 42 access token never reaches the browser: used once for `/me`, then our own HS256 JWT is issued in an httpOnly cookie. Frontend (:3000) and API (:9000) are same-site on localhost, so SameSite=Lax cookies work for fetch.
- `api/vendor/42api/_sync/` is generated from `_async/` — edit async + regenerate, never hand-edit sync.
- Both themes share layout + semantic token NAMES; only values swap under `[data-theme]` (globals.css). Palettes copied verbatim from `assets/`.
- Python 3.14 in this env: all wheels (asyncpg 0.32, pydantic 2.14, etc.) install fine.
- Alembic env uses async engine + `DIRECT_URL` (asyncpg), coercing the driver; leaves sqlite URLs untouched for tests.
- Notifications are **stored** (unlike 42 profiles, which stay live from the API) — they're app-local social events with their own read-state and fan-out. Delivery is poll-based (bell polls `unread-count`); event creation happens in the routers after the mutation, keeping `services/` single-purpose and dependencies inward (notifications service imports only models/schemas). The "Tutti"/`all` post scope fans out one row per opted-in user — fine at campus scale.
